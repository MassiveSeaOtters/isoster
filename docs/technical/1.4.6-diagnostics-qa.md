# §1.4.6 Diagnostics, QA, and reproducibility infrastructure

The features described in §1.4.1 through §1.4.5 modify what ISOSTER
computes. The features in the present subsection support how those
computations are *inspected, validated, and reproduced* — they do
not change the algorithm itself but they make every fit the
algorithm produces traceable, comparable, and replayable. None of
these features is novel in the sense of replacing a missing piece
of the classical algorithm; rather, they are the operational
infrastructure that distinguishes a research code from a research
*tool*, and they are part of the technical-section discussion
because survey-pipeline use of ISOSTER will rest on them at least
as much as on any algorithmic feature.

Four pieces of infrastructure are worth describing: the stop-code
domain that uniformly summarizes per-isophote outcomes; the QA
plotting subsystem that includes a cross-tool comparison facility
for ISOSTER, `photutils.isophote`, and AutoProf; the serialization
layer that supports three on-disk formats with a common
configuration round-trip property; and the exhausted-benchmark
framework that drives the cross-tool benchmark chapters of this
paper.

## §1.4.6.1 Stop codes as a per-isophote outcome summary

Every isophote in an ISOSTER output dictionary carries a `stop_code`
field drawn from $\{0, 1, 2, 3, -1\}$. The five values encode the
five algorithmically distinct outcomes the per-isophote fit loop
can produce:

| Code | Meaning | Trigger |
|------|---------|---------|
| $0$  | Success | Converged: $\lvert a_\max\rvert < c \cdot \sigma_\mathrm{eff}$ with $i \ge \mathtt{minit}$ |
| $1$  | Too many flagged samples | $\mathtt{actual\_points} < \mathtt{total\_points} \cdot (1 - \mathtt{fflag})$ |
| $2$  | Max-iteration fallback | Reached $\mathtt{maxit}$; best-so-far geometry returned |
| $3$  | Too few points | Fewer than 6 valid samples for the five-parameter harmonic fit |
| $-1$ | Gradient failure | Outward-only two-strike rule on gradient diagnostics, or $\widehat{dI/da} = 0$ |

The codes are not interchangeable. A stop code of $0$ indicates
that the isophote met the convergence criterion and that the
reported geometry is the converged geometry. A stop code of $2$
indicates that the iteration count was exhausted; the reported
geometry is the *best so far* (the iteration with the smallest
effective amplitude — §1.1), which is usually within a small
fraction of the convergence threshold but not necessarily there.
Codes $1$ and $3$ indicate sample-population problems — too many
masked or sigma-clipped pixels, or too few valid samples for the
linear system — and the fit returns a geometry that is the best
attempt under degraded conditions but does not carry the
statistical guarantees of a code-$0$ converged fit. Code $-1$
indicates a gradient-related failure that terminated the fit
attempt without producing a usable geometry.

The driver applies a uniform policy across the regular-mode growth
loops: codes $\{0, 1, 2\}$ are *acceptable* and propagate as the
starting geometry for the next SMA step; codes $\{3, -1\}$ are
*unacceptable* and terminate the current growth direction. The
acceptable set is exposed as the module-level constant
`ACCEPTABLE_STOP_CODES`. This policy is identical between the
inward and outward loops and between the regular and template-
forced modes, so a consumer of the output dictionary can filter
isophotes by stop code with a single rule:

```python
good   = [iso for iso in results["isophotes"] if iso["stop_code"] == 0]
usable = [iso for iso in results["isophotes"] if iso["stop_code"] in {0, 1, 2}]
failed = [iso for iso in results["isophotes"] if iso["stop_code"] < 0]
```

The same stop-code domain applies to the multi-band joint fit
(§1.4.5), where each isophote carries one shared stop code derived
from the joint-fit convergence rather than per-band stop codes;
the multi-band stop code reports whether the *shared geometry*
converged, not whether any one band's intensity extraction
succeeded.

A property worth flagging: the stop-code domain is *closed under
the §1.4 features*. None of the new features in this section adds
new stop codes, and none of them changes the trigger for an
existing stop code. The LSB auto-lock of §1.4.3 commits to a
locked clone after detecting a gradient-failure trend, but the
locked-clone isophotes themselves still report stop codes from the
same five-value domain (typically code $0$ since the geometry is
fixed and the fit reduces to a forced extraction). The variance-
aware WLS path of §1.4.2 changes the value of $\sigma_\mathrm{eff}$
that enters the code-$0$ convergence criterion but not the criterion
itself. The closure is intentional: a consumer of the results
dictionary can rely on the stop-code domain being a stable contract
across the configuration surface.

## §1.4.6.2 QA plotting and cross-tool comparison

ISOSTER ships with a QA plotting subsystem in `isoster/plotting.py`
that takes one or more results dictionaries and produces a
standardized multi-panel figure summarizing the fit. Two public
entry points are exposed.

The first, `plot_qa_summary`, takes a single results dictionary and
the corresponding image and renders a six-panel figure with the
image and overlaid isophotes, the surface-brightness profile, the
ellipticity and position-angle profiles, the higher-order harmonic
profiles in their Bender-normalized form, and the residual map
(image minus reconstructed model). This is the standard
single-galaxy inspection figure; it is the visual unit ISOSTER
returns to the user when a fit has been completed and the user
wants to look at it.

The second, `plot_comparison_qa_figure`, takes two or three results
dictionaries — typically one each from ISOSTER, `photutils.isophote`,
and AutoProf — and produces the same six-panel layout with each
panel showing all methods overlaid in a color-consistent style. The
function auto-detects the layout mode (solo, 1-vs-1, or three-way)
from the number of supplied dictionaries, applies cross-method
position-angle anchoring (to ensure the three methods' PA estimates
are reported on a common branch of the $[0, \pi)$ ambiguity), and
applies the per-method visual style from a small `METHOD_STYLES`
table at the top of `plotting.py` so the visual conventions are
consistent across the figure. This is the figure that drives the
visual comparison studies in the cross-tool benchmark chapters.

A subtlety worth flagging is the *harmonic-coefficient convention
dispatch*. Different tools report different higher-harmonic
quantities: ISOSTER in φ-mode reports image-azimuth-space
coefficients; ISOSTER in ψ-mode and `photutils.isophote` both
report eccentric-anomaly-space coefficients; AutoProf reports its
coefficients in a basis that has not yet been ported to the
Bender-normalized convention. The QA plotting code therefore
applies a per-tool dispatch on the harmonic-contour overlay step:
ISOSTER φ-mode contours are drawn in image-azimuth space, ISOSTER
ψ-mode and `photutils.isophote` contours are drawn in eccentric-
anomaly space, and AutoProf contours fall back to pure ellipses
without higher-order shape correction until its coefficient scale
is matched. The dispatch is documented in `METHOD_STYLES` and is
visible to the figure consumer through a legend annotation.

The Bender-normalized convention $A_n^\mathrm{norm} = -A_n / (a
\cdot dI/da)$ is applied *uniformly* at plot time across all tools
that report compatible raw coefficients. This is the convention of
§1.1 — raw $A_n / B_n$ values are not directly interpretable
because their magnitudes scale with the local intensity profile —
and applying it uniformly is what makes the cross-tool comparison
plots meaningful. The multi-band case (§1.4.5) extends the
convention to per-band normalization using the per-band local
gradient, producing band-distinct normalized curves even when the
raw coefficient is shared.

A `build_method_profile` helper standardizes the input formats:
some tools deliver isophote lists, others deliver array dicts, and
the comparison figure needs a common profile format. The helper
absorbs the format conversion and lets the figure-construction
code operate on a single canonical representation.

## §1.4.6.3 Reproducible serialization

ISOSTER provides three serialization paths for results
dictionaries. All three share the property that the saved file
contains enough information to *re-execute the fit bit-for-bit*
from the file alone — no out-of-band configuration is needed. The
property is enforced through a common helper layer in
`isoster/_shared.py` that serializes the resolved `IsosterConfig`
into a JSON-encoded $(\mathtt{PARAM}, \mathtt{VALUE})$ table.

The FITS path, `isophote_results_to_fits`, writes a three-HDU
file: a `PrimaryHDU` (empty), a `BinTableHDU` named `ISOPHOTES`
with one row per isophote, and a `BinTableHDU` named `CONFIG`
with the two-column $(\mathtt{PARAM}, \mathtt{VALUE})$ layout
carrying the full configuration. The third HDU is the key to the
round-trip property: every field of the `IsosterConfig` object
that produced the fit is recorded, with no reliance on
`IsosterConfig`'s default values. A future ISOSTER release that
adjusts a default value cannot silently change the meaning of an
existing FITS file, because the file carries the explicit value
that was in effect at write time.

The ASDF path, `isophote_results_to_asdf`, performs the same
serialization in ASDF's tree format, which preserves native Python
types (in particular, nested dicts and numpy arrays) more
transparently than FITS. For the multi-band schema (§1.4.5), the
per-band column proliferation reads more naturally in ASDF's tree
than as flat FITS columns, and the ASDF writer is the recommended
multi-band path.

The third path, `isophote_results_to_astropy_tables`, returns the
isophote list as an `astropy.table.Table` without writing to disk.
This is the API path for downstream analysis code that wants the
isophote data without round-tripping through a file. The table
carries the same column set as the FITS `ISOPHOTES` HDU; the
`config` field is dropped, since an in-memory results dictionary
already carries the resolved `IsosterConfig` object.

All three readers (`isophote_results_from_fits`,
`isophote_results_from_asdf`, and the analogous multi-band variants)
detect legacy files where the `CONFIG` block was written as FITS
header keywords (an earlier ISOSTER release) or as a missing block
(an even earlier release) and reconstruct what they can. The
forward-compatibility convention is that fields recognized by the
current release are honored; fields not recognized are silently
dropped with a `UserWarning`. This is the right policy for
reading the field of a future release on an older ISOSTER install:
the read succeeds, the recognized fields are honored, and the user
is informed that some configuration metadata was discarded.

The round-trip property has a concrete benefit for the benchmark
chapters of this paper. The benchmark campaigns process thousands
of galaxies, store the per-galaxy fit outputs as FITS or ASDF
files, and downstream analyses (composite scoring, residual model
construction, cross-tool comparison) re-read those files. The
guarantee that the file is sufficient to re-execute the fit
removes a class of reproducibility failures — fits being compared
under subtly different default values, defaults changing between
ISOSTER releases without the user noticing — that would otherwise
need to be controlled externally.

## §1.4.6.4 The exhausted-benchmark framework

The benchmark chapters of this paper rest on a YAML-driven
campaign framework documented in `docs/09-exhausted-benchmark.md`
and implemented in `benchmarks/exhausted/`. We summarize it here
because several features in §1.4 are evaluated against it.

The framework operates on the principle that benchmark
configurations should be *enumerable* — each combination of
tool, configuration, and input mock is given a YAML "arm"
specification, the arms are executed independently and produce
per-arm outputs in a deterministic directory layout, and the
analysis-side scoring code reads from those outputs to compute
per-arm and cross-tool composite scores. The deterministic layout
plus the round-trip serialization property of §1.4.6.3 together
guarantee that a benchmark result can be reproduced from the YAML
arm specification and the input mock alone.

Two scoring modes are supported. The *within-tool* composite score
includes method-specific health terms (e.g., a per-tool stop-code
penalty for ISOSTER, a per-tool convergence-iteration penalty for
AutoProf) and is used for the per-tool ablation studies (which
ISOSTER configuration is best on this sample). The *cross-tool*
score includes only tool-neutral residual and runtime terms, and
is used for the head-to-head comparisons of ISOSTER, photutils,
and AutoProf (which tool best fits the sample under each tool's
recommended configuration). The two modes use the same per-galaxy
data products but different scoring functions; the separation
makes the cross-tool comparisons fair by excluding terms that
favor any one tool's diagnostic ontology.

Three campaign datasets are processed through the framework: the
Huang2013 mocks of nearby elliptical galaxies (multi-Sersic
models, varying resolution and noise), the S4G mocks of nearby
galaxies (300 late-type-focused systems, multi-component models),
and the SGA-2020 real galaxies on LegacySurvey imaging (~2,000
galaxies, real-data robustness). The campaigns are described in
detail in the benchmark chapters of this paper and are not
re-described here; the relevance for the present subsection is
that all three campaigns use the same exhausted-benchmark
framework, the same serialization formats, and the same
QA plotting subsystem. A reader who wants to inspect the
per-galaxy outputs of any campaign can re-read the saved fits
and apply `plot_qa_summary` or `plot_comparison_qa_figure` to
reproduce any QA figure in the paper. The infrastructure for
inspection and the infrastructure for benchmarking are the same
infrastructure.

## §1.4.6.5 Closing remarks on §1.4

This concludes the survey of new features in §1.4. The six
subsections cover what ISOSTER does *differently* from the
classical algorithm — eccentric-anomaly sampling and ISOFIT-style
joint harmonics (§1.4.1), variance-aware WLS fitting (§1.4.2),
the low-surface-brightness outskirt strategy (§1.4.3),
operations-grade batch robustness primitives (§1.4.4), the
multi-band joint free fit (§1.4.5), and the diagnostics and
reproducibility infrastructure (§1.4.6). Each feature is opt-in,
composable with every other feature, and reduces to the classical
behaviour under its disabled-default configuration.

The features were developed in the order they are presented:
§1.4.1 and §1.4.2 came first because they are direct
generalizations of well-established algorithmic ideas (Ciambur
2015; classical statistical estimation theory); §1.4.3 came next
to address the LSB-regime failure modes that motivated the
development of ISOSTER for HSC-SSP science; §1.4.4 followed when
the survey-scale deployment of ISOSTER exposed the failure modes
the robustness primitives address; §1.4.5 was developed once the
single-band feature set had stabilized; §1.4.6 was iterated
throughout to support the benchmark and QA needs of the paper
this subsection is part of. The historical order is not the
recommended-reading order for users, but it is informative for
understanding which features are mature (§1.4.1, §1.4.2) and
which are still being refined on new data (§1.4.3's
parameter defaults; §1.4.5's loose-validity calibration).

§1.5 turns to the comparison of ISOSTER, on a feature-by-feature
basis, against `photutils.isophote`, AutoProf, and IRAF
`Isofit`. The comparison rests on the features described in §1.4
and on the algorithmic-speed argument of §1.3; the quantitative
performance comparisons come from the benchmark chapters that
follow this technical section.
