# §1.3 Why ISOSTER is fast

ISOSTER and its Python predecessors implement the same underlying
Jedrzejewski (1987) algorithm. The runtime difference between them is
therefore not a difference in *what* is being computed but in *how*
that computation is organized across Python, C, and JIT-compiled code,
and in how much of it the implementation is willing to amortize across
iterations and across the three callers (regular fitting, forced
extraction, and 2-D model reconstruction) that all need elliptical
sampling. This section explains the four algorithmic choices that
together account for the speed gap. Concrete numerical comparisons
across image size, sampling density, and configuration combination
live in the separate benchmark chapters that draw from the Huang2013,
S4G, and SGA2020 campaigns; here we focus on the *reasons*.

## §1.3.1 Where Python predecessors spend their time

Three patterns dominate the runtime of the existing Python
elliptical-isophote stack. We name them at the abstraction level of
"loops vs vectors" rather than by specific function name, since
implementations evolve and a citation to a function name in a release
notes section would age out within a release cycle.

**Per-point Python-level sampling.** The classical formulation samples
intensity at $N$ points around each trial ellipse. A direct
implementation evaluates each point through a Python-callable
integrator that pulls a small neighborhood of pixels out of the image
and returns either the bilinear-interpolated central value or a small
area integral. With $N$ on the order of $2\pi a$, an isophote at
$a = 100\,\mathrm{px}$ requires more than six hundred such calls *per
iteration*, and there are typically ten to thirty iterations per
isophote and tens to hundreds of isophotes per image. Each call is
fast in absolute terms but carries Python interpreter overhead, and
the cumulative cost is what dominates wall time at the image level.

**Redundant gradient evaluation.** The geometry-update step needs the
local radial intensity gradient $dI / da$, estimated by sampling the
image at two SMAs offset above and below the current one. In the
classical algorithm this gradient is re-evaluated *on every
iteration*, even though the geometry typically changes by a few
percent per iteration once it has approximately settled. Each
gradient evaluation costs two additional sampling passes — that is,
two extra ellipses sampled at $N$ points each — so the gradient alone
roughly triples the sampling cost per iteration in the classical
formulation.

**Three independent sampling code paths.** Regular fitting, forced
photometry extraction, and 2-D model reconstruction all need to
sample the image along elliptical paths, but for historical reasons
each one is implemented in its own module with its own sampling
helpers. The same operation — "compute the pixel coordinates of $N$
points along an ellipse with parameters $(x_0, y_0, a, \varepsilon,
\mathrm{PA})$ and look up the image intensities at those points" — is
written and tested three times. The duplication is not just a
code-maintenance liability; it also means that an optimization
applied to one caller does not automatically benefit the others, and
that the three call sites can drift in their conventions
(half-pixel offsets, boundary handling, mask treatment) until they
disagree on what "the same isophote" means.

These three patterns compound. A fit at moderate image size and SMA
density is bottlenecked by tens of thousands of Python-level sampling
calls, each of which is redundantly invoked through one of three
parallel code paths. None of them is individually fatal, but together
they set the wall-clock floor.

## §1.3.2 What ISOSTER does differently

ISOSTER replaces all three patterns with four algorithmic choices.
Each is independently a speedup; together they form the core of the
performance argument.

### Vectorized path-based sampling

The first and most fundamental change is to replace the per-point
sampling loop with a single vectorized call into
`scipy.ndimage.map_coordinates`. Given an image array and an array of
$N$ fractional pixel coordinates $(x_j, y_j)$, `map_coordinates`
evaluates a $k$-th order spline interpolation at all $N$ points in a
single C-level pass, returning the intensity vector
$\mathbf{I} \in \mathbb{R}^N$ as a NumPy array. ISOSTER uses cubic
interpolation by default, which matches the accuracy of the area
integrators used in the classical formulation while collapsing the
Python loop into one external call. The coordinate array itself is
computed analytically from the ellipse parameters in a few NumPy
operations:

$$
x_j = x_0 + a \cos\theta_j \cos\mathrm{PA} -
              a(1-\varepsilon) \sin\theta_j \sin\mathrm{PA},
$$
$$
y_j = y_0 + a \cos\theta_j \sin\mathrm{PA} +
              a(1-\varepsilon) \sin\theta_j \cos\mathrm{PA},
$$

so the entire sampling pipeline — coordinates, interpolation, and
mask application — is a small constant number of NumPy / SciPy calls
per isophote regardless of $N$. The Python interpreter is involved
only in launching the call, not in iterating over the $N$ points.

This single change accounts for the largest share of the speed gap
between ISOSTER and the direct Python predecessor. It is also the
choice that fixes the loop overhead *exactly* — there is no "Python
loop with $N$ iterations" left in the sampling layer at all. The
remaining Python loops in the fit are over iterations of the per-SMA
solver, which numbers in the tens, not over sample points, which
number in the hundreds.

### Numba-accelerated inner kernels

A small number of operations sit between sampling and convergence
checking that are awkward to vectorize cleanly in NumPy but are
trivially expressible as JIT-compiled loops. The chief examples are
the harmonic design-matrix builder
$\mathbf{A} = [\mathbf{1}, \sin\theta, \cos\theta, \sin 2\theta,
\cos 2\theta]$ for the five-parameter geometry fit, the joint
multi-band design-matrix builder for the $B$-band case (§1.4.5), and
the dominant-coefficient selector that scans
$\max(|A_1|, |B_1|, |A_2|, |B_2|)$ along with the bookkeeping that
distinguishes which axis is being updated. ISOSTER implements these
with Numba `@njit` decorators in `isoster/numba_kernels.py` so that
each one compiles to a tight loop in machine code at first call, then
runs at speeds comparable to a hand-written C implementation.

Two implementation properties are worth flagging. First, every Numba
kernel has a byte-equivalent NumPy fallback in the same file: if the
Numba import fails or the user explicitly disables it, the fallback
is dispatched transparently and produces identical numerical output.
This matters for reproducibility on systems where LLVM is unavailable
and for the configuration where ISOSTER is run on a small number of
galaxies — Numba's first-call JIT compilation costs roughly a second,
which can be a net loss when only one galaxy is being fitted.
Second, the kernels are deliberately *small*. The Numba-compiled
region is the design-matrix construction and the dominant-coefficient
scan; the linear solve itself is delegated to NumPy's
`numpy.linalg.lstsq`, which already wraps LAPACK. We do not attempt
to JIT-compile the solver, because doing so would require duplicating
LAPACK behaviour inside Numba for no measurable gain.

### Lazy gradient evaluation

The radial gradient $dI / da$ is the single most expensive quantity
in the per-iteration cost budget, because evaluating it requires two
additional sampling passes at SMAs offset from the current isophote.
The classical formulation re-evaluates it every iteration. ISOSTER
instead computes the gradient on iteration $i = 0$, caches the value,
and reuses it on every subsequent iteration of the same isophote
*unless* the convergence diagnostic — the dominant harmonic amplitude
$|a_\max|$ — fails to improve for three consecutive iterations. When
that happens, ISOSTER re-evaluates the gradient and resets the
counter.

The justification is that the gradient is a local property of the
image at the current geometry. Once the iteration is reasonably close
to the converged isophote, the geometry moves by a few percent per
iteration and the gradient changes by even less, because the
gradient is itself a slowly-varying function of $a$ in the regime
where the fit is well-conditioned. Re-evaluating the gradient under
those conditions is computational waste. The three-iteration stall
detector is an inexpensive safeguard for the case where the cached
gradient is meaningfully wrong — for example, when the iteration has
wandered into a region of low gradient SNR — and re-evaluation
restores the classical algorithm's behaviour in those cases at the
cost of a few extra sampling passes per affected isophote.

This is the only change in §1.3.2 that is *not* purely a software
engineering optimization. It modifies the algorithm itself, in the
sense that the sequence of intermediate geometries an isophote moves
through differs from the classical formulation. The converged
geometry, the harmonic coefficients reported, and the convergence
criterion are all identical; only the trajectory through iteration
space is shorter. We have validated this empirically by disabling
the lazy gradient (the configuration flag `use_lazy_gradient=False`
restores the classical behaviour) and confirming that the per-SMA
output dictionaries match within numerical tolerance.

### Shared sampling stack

The fourth change addresses the three-paths-doing-the-same-thing
pattern of the classical Python implementations. ISOSTER has one
sampling module (`isoster/sampling.py`) that exposes one entry point
(`extract_isophote_data`) and one return type (`IsophoteData`). All
three callers route through it:

- **Regular fitting** (`isoster/fitting.py`) calls it on each
  iteration of each isophote.
- **Forced photometry extraction** (`extract_forced_photometry` in
  the same module) calls it once per template isophote with the
  template geometry held fixed.
- **2-D model reconstruction** (`isoster/model.py`'s
  `build_isoster_model`) calls it to evaluate the harmonic-encoded
  intensity model at each isophote when reconstructing a smooth 2-D
  image from the per-SMA fit.

A bug fix to mask treatment, a change to the boundary-handling
convention, or an optimization to the coordinate-construction
arithmetic now lands once and benefits all three callers
simultaneously. The half-pixel offset convention is enforced in one
place. The sampling output schema — what `IsophoteData` carries — is
the same everywhere it appears in the codebase.

This is a software-engineering argument, not directly an
algorithmic-speed argument. But it has two concrete performance
consequences. First, optimizations to the shared sampling stack
amortize across all three callers; in particular, the
vectorized-`map_coordinates` choice automatically benefits forced
photometry and model reconstruction in addition to regular fitting,
which is significant because forced photometry is the dominant
workflow in multi-band survey pipelines. Second, the multi-band
extension (§1.4.5) was buildable as a parallel module precisely
because the single-band sampling stack was self-contained: the
multi-band path imports the low-level coordinate helpers without
having to also import three callers' worth of historical
peculiarities.

## §1.3.3 Algorithmic complexity and where it goes

The four choices in §1.3.2 do not change the asymptotic complexity
of the algorithm — they reduce the constant factors. It is worth
naming the asymptotic structure explicitly so that the speed argument
can be quantified later without ambiguity.

Per-isophote cost is dominated by two terms. The sampling step
performs $N = \max(64, \lceil 2\pi a \rceil)$ interpolations through
one `map_coordinates` call, costing $\mathrm{O}(N)$ in image-area
terms and $\mathrm{O}(1)$ in the Python interpreter. The linear-system
solve is $\mathrm{O}(p^2 N)$ where $p$ is the number of fit
parameters (five for the geometry-only fit, $5 + 2L$ for an extended
ISOFIT fit with $L$ higher orders, and $B + 4 + 2L$ for a multi-band
joint fit with $B$ bands; see §1.4.1 and §1.4.5). Both terms are
linear in $N$, so per-isophote cost is asymptotically linear in the
semi-major axis $a$ and effectively independent of image area beyond
what enters through `map_coordinates`' interpolation kernel.

Image-level cost is the per-isophote cost summed over the inward and
outward growth loops. Let $K$ be the number of isophotes (typically
of order 50 in a geometric-stepping fit from $a_0 = 10\,\mathrm{px}$
to $a_\max = 200\,\mathrm{px}$ with `astep = 0.1`), and let
$\overline{m}$ be the average per-isophote iteration count.
Worst-case total cost is
$\mathrm{O}(K \cdot \overline{m} \cdot N_\max)$ where $N_\max$ is the
sample count at the largest SMA. In practice $\overline{m}$ is well
below the configured `maxit` because most isophotes converge in
under twenty iterations, and the lazy-gradient optimization makes
$\overline{m}$ matter less because each additional iteration costs
just one sampling pass rather than three.

The two consequences worth pointing out:

- **Image area enters only through `map_coordinates` interpolation
  cost.** The interpolation kernel reads a small neighborhood
  ($k+1$ pixels per dimension for a $k$-th order spline) around each
  of the $N$ sample points. The total pixel reads per isophote is
  therefore $\mathrm{O}(N \cdot k^2)$ — sublinear in the image area
  for any modern image size. This is why the fit time scales with
  the number of isophotes and the typical semi-major axis, not with
  the image dimensions, in the regime where the galaxy occupies a
  small-to-moderate fraction of the image.

- **Sampling density and ISOFIT cost.** The user-facing knobs that
  most strongly affect runtime are `astep` (geometric SMA step,
  which sets $K$) and the harmonic-fit configuration (which sets
  $p$, and therefore the LAPACK solve cost). The ISOFIT path with
  `harmonic_orders=[3, 4]` carries $p = 9$ rather than $p = 5$,
  raising the solve cost by a constant factor that the benchmark
  chapters quantify in absolute terms.

The point of this complexity sketch is not to predict wall time but
to clarify which knobs in `IsosterConfig` are the runtime-relevant
ones. The benchmark chapters then quantify the constants.

## §1.3.4 Correctness guarantees alongside speed

The performance argument is only useful if the faster code computes
the same thing as the slower code where the algorithm overlaps.
ISOSTER provides three guarantees that together establish this:

1. **OLS path byte-identical when `variance_map = None`.** The
   weighted-least-squares (WLS) machinery introduced in §1.4.2 is
   only engaged when the user supplies a variance map; in its
   absence, the linear-system solve runs through the same OLS code
   path that would run in any classical implementation, and produces
   identical output to within the floating-point determinism of
   LAPACK on the host platform. The configuration flag is therefore
   binary at the algorithm-correctness level: `variance_map` is
   either supplied (WLS) or it is not (OLS), and the two paths share
   no shared mutable state.

2. **Round-trip serialization is identity-preserving.** Saving a
   fit through `isophote_results_to_fits` and reading it back
   through `isophote_results_from_fits` reproduces the original
   results dictionary; the same is true for the ASDF writer-reader
   pair. The reproducibility property extends one step further: the
   `CONFIG` HDU of the FITS file carries the full `IsosterConfig`
   as JSON-serialized `(PARAM, VALUE)` rows, so a fit can be
   re-executed bit-for-bit from the file alone, with no implicit
   default-value drift between releases.

3. **Comprehensive regression-test coverage.** The test suite pins
   the algorithmic outputs at the per-SMA dictionary level for a
   reference panel of synthetic galaxies, including the byte-equivalence
   property of the Numba and NumPy fallback kernels and the
   classical-vs-lazy-gradient equivalence at the converged-output
   level. The test panel is run on every commit, and the byte-level
   reference outputs are stored in the repository so that a future
   refactor that silently changes algorithmic behaviour cannot pass
   review.

What §1.3.4 does *not* claim is a specific numerical-agreement number
with `photutils.isophote`, `Isofit`, or `AutoProf`. Those numerical
comparisons are quantitative empirical questions that the benchmark
chapters answer for representative samples; here we establish only
that the ISOSTER implementation is internally consistent and that its
fast paths produce the same outputs as its slow paths.
