# §1.2 Implementation overview

## Module organization

The package is organized into a small core and a multi-band parallel
tree. The core comprises six Python modules that map cleanly to the
algorithm description in §1.1:

| Module | Role |
|--------|------|
| `isoster/driver.py` | Image-level orchestration. Implements the central-pixel → anchor → inward → outward → CoG pipeline, the mode-selection switch, and the propagation of inherited geometry between SMAs. |
| `isoster/fitting.py` | Per-isophote fitting loop. Runs the iteration sketched in §1.1, applies geometry updates with damping and step clipping, attaches optional post-hoc blocks (higher-order harmonics, parameter errors, aperture metrics). |
| `isoster/sampling.py` | Vectorized ellipse sampling through `scipy.ndimage.map_coordinates`. Computes the ellipse coordinates, performs mask-aware sampling, and returns `IsophoteData` objects carrying $(\theta, \phi, I, r, \sigma^2)$. |
| `isoster/config.py` | `IsosterConfig` Pydantic schema. Sixty-two parameters in sixteen functional groups; cross-parameter validators (e.g. $\mathtt{minit} \le \mathtt{maxit}$, `lsb_sma_threshold` required when `integrator='adaptive'`). |
| `isoster/model.py` | 2-D model reconstruction by radial interpolation between converged isophotes. Auto-detects whether eccentric-anomaly sampling was used and selects the correct harmonic-evaluation basis. |
| `isoster/numba_kernels.py` | Optional Numba-JIT inner kernels (harmonic design-matrix builder, ellipse-coordinate construction, harmonic-model evaluation, eccentric-anomaly conversion). Falls back to byte-equivalent NumPy implementations when Numba is absent. |

Auxiliary modules round out the core: `isoster/cog.py`
(curve-of-growth assembly with crossing detection),
`isoster/utils.py` and `isoster/_shared.py` (serialization
helpers, FITS / ASDF writers and readers, plus the estimator helpers
that single-band and multi-band must agree on), `isoster/plotting.py`
(QA figures, including cross-tool comparison panels for
`photutils.isophote` and AutoProf alongside ISOSTER), and
`isoster/optimize.py`, a thin façade that re-exports the per-isophote
primitives (`fit_isophote`, `compute_gradient`, `compute_deviations`,
`extract_isophote_data`, …) at a stable import path. That façade
matters for the input-validation discussion of §1.4.2.3: those
functions are public, so they may legitimately be handed a raw,
unvalidated variance map, which is why the sanitization guarantees
`fit_image` provides internally cannot simply be assumed downstream.

The multi-band parallel tree (`isoster/multiband/`) is a sibling
package: it imports a handful of low-level helpers from the core
modules but provides its own driver, fitting loop, sampling stack,
configuration schema, and Numba kernels, and exposes a separate
CLI entry point (`isoster-mb`). This separation is by design — the
joint-multi-band path is algorithmically different enough from
single-band that sharing the per-SMA loop would have produced an
unmaintainable mass of conditionals, and the multi-band path carries
operational failure modes (per-band mask asymmetry, a variance map
missing in one band, misalignment) that have no single-band
counterpart. We describe the joint multi-band algorithm in §1.4.5.

## Canonical user-facing call

The entire public API for the single-band case is one function and
one Pydantic configuration object. A typical free-fit looks like:

```python
from isoster import fit_image, isophote_results_to_fits
from isoster.config import IsosterConfig

config = IsosterConfig(sma0=10.0, maxsma=200.0, full_photometry=True)
results = fit_image(image, mask=mask, config=config, variance_map=var)
isophote_results_to_fits(results, "galaxy_isophotes.fits")
```

Every algorithmic feature described in §1.4 — eccentric anomaly,
ISOFIT, WLS, LSB auto-lock, outer-region regularization, batch
retry policies — is enabled by flipping a flag on `IsosterConfig`.
There is no separate "expert API" with a different signature; the
beginner's call and the survey-pipeline call differ only in how
many config flags are set.

## Mode selection

The single user-level mode switch is *template vs regular*:

| Trigger | Mode | Internal driver |
|---------|------|-----------------|
| `template` argument provided | Template-based forced photometry | `_fit_image_template_forced` |
| Otherwise | Regular iterative free fit | inline in `fit_image` |

`template` accepts three forms: a results dictionary (the typical
"reuse band-A geometry on band B" call), a list of isophote dicts
(custom-SMA forced extraction), or a path to a previously saved
FITS file (cross-pipeline portability). The deprecated alias
`template_isophotes` is still accepted for backwards compatibility.

## Output schema and serialization

`fit_image` returns a dictionary. The two mandatory keys are
`isophotes` (a list of per-SMA dicts, sorted by ascending
semi-major axis) and `config` (the resolved `IsosterConfig` object).
Each isophote dict carries a fixed set of always-present geometry,
intensity, and stop-code fields plus a set of optional blocks
controlled by configuration flags (higher-order harmonics, aperture
metrics, curve-of-growth, debug diagnostics, LSB lock markers).
The full per-field reference lives in the user guide; the present
section emphasizes the *invariants* that downstream tools can rely
on:

- The list is sorted by ascending semi-major axis.
- The central pixel (when $a_\mathrm{min} \le 0$) is always
  prepended as a single dict with $\mathtt{sma} = 0$.
- Stop codes are drawn from $\{0, 1, 2, 3, -1\}$ with documented
  triggers (§1.4.6); the constants
  $\mathtt{ACCEPTABLE\_STOP\_CODES} = \{0, 1, 2\}$ define which
  codes propagate geometry into the next SMA step.
- Higher-order harmonic amplitudes, when present, are reported in
  the Bender-normalized form
  $A_n^\mathrm{norm} = -A_n / (a \cdot dI/da)$. The raw $A_n$ are
  scale-dependent and not directly comparable across SMAs; we
  follow the convention used throughout the isophote-analysis
  literature.

Three serialization paths are provided, of which two are archival
and one is a convenience: `isophote_results_to_fits`
writes a four-HDU FITS file with `PrimaryHDU`, a `BinTableHDU`
named `ISOPHOTES`, a `BinTableHDU` named `CONFIG` carrying the
full configuration as JSON-serialized `(PARAM, VALUE)` rows, and a
`BinTableHDU` named `META` carrying the remaining top-level result
keys in the same JSON row format, so that information which is
neither per-isophote nor a configuration field (lock state,
first-isophote retry outcomes, outer-region references) survives the
round trip rather than being silently dropped;
`isophote_results_to_asdf` writes the same information in ASDF
format, preserving native Python types (particularly useful for
nested dicts and numpy arrays in the multi-band schema); and
`isophote_results_to_astropy_tables` returns the isophote list as
an `astropy.table.Table` for downstream analysis without going
through disk — the table carries the isophote columns only, and
deliberately drops the configuration and the run metadata, so it is
an analysis convenience rather than an archival format. The two
on-disk writers share a common helper layer in
`isoster/_shared.py` to guarantee that the same configuration
object yields the same serialized configuration content in either
format. This matters for the reproducibility argument of §1.3.4:
the saved `CONFIG` block records the *resolved* configuration —
every field, including those left at their defaults — so re-running
the fit does not depend on the defaults of whichever ISOSTER release
happens to be installed. It is worth being exact about the scope of
that claim. The file records the configuration, not the experiment:
the input image, mask and variance map, the ISOSTER version, and the
numerical environment (BLAS/LAPACK build, Numba availability) all
sit outside it. Reproducing a fit means supplying those separately
and pairing them with the saved configuration.

## Configurability surface

`IsosterConfig` carries 62 parameters across 16 functional groups
(geometry initialization, SMA control, fitting control, geometry
update control, quality control, constraints, outputs and features,
integration mode, eccentric-anomaly sampling, higher-order
harmonics / ISOFIT, geometry update strategy, central region
regularization, outer-region center regularization, permissive
geometry mode, first-isophote robustness, automatic LSB geometry
lock). Cross-parameter validators
reject inconsistent combinations at construction time — for
example, `integrator='adaptive'` raises `ValidationError` without
an accompanying `lsb_sma_threshold`, and `lsb_auto_lock=True`
rejects combination with any of `fix_center`, `fix_pa`, `fix_eps`.
The guiding principle is that an `IsosterConfig` that successfully
constructs cannot produce a behavior that is intrinsically
self-contradictory. This pushes a meaningful fraction of the
"misconfigured run" failure mode out of the runtime path and into
the configuration path, where the error message points the user at
the exact field involved.

`IsosterConfig` is an ordinary mutable Pydantic model — assigning to
a field on an existing instance works — so the guarantee ISOSTER
offers is about *behaviour*, not about the type: `fit_image` never
mutates the config it receives. Where the driver needs different
settings mid-fit (for example, the LSB auto-lock needs
`fix_center=fix_pa=fix_eps=True` once the lock commits) it derives a
clone via `config.model_copy(update={...})` and uses that, leaving
the caller's object untouched. The original therefore remains usable
for a subsequent fit on a different image without surprises. What
is *not* guaranteed is that a config cannot change under the user,
and the gap is wider than it looks. `IsosterConfig` does not enable
Pydantic's `validate_assignment`, so post-construction assignment
runs *no* validation at all: neither the cross-field rules nor even
the per-field constraints. `config.sma0 = -5.0` is accepted on an
existing instance although `IsosterConfig(sma0=-5.0)` raises
`ValidationError`, and `config.integrator = 'adaptive'` is accepted
without the `lsb_sma_threshold` the constructor would demand. The
validation guarantee of the previous paragraph is therefore a
guarantee about *construction*. Building a fresh `IsosterConfig` is
the supported way to change settings, and a pipeline that mutates a
config in place forfeits the protection this section is about.

This is the entire user-visible interface. §1.3 turns to what
happens inside that interface and how it compares with the direct
Python predecessor.
