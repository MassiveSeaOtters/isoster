    §1.3 Why ISOSTER is fast

    ISOSTER and its Python predecessors implement the same underlying Jedrzejewski (1987) algorithm. Most of the runtime difference between them is therefore not a difference in what is being computed but in how that computation is organized across Python, C, and JIT-compiled code — with one exception, the lazy gradient below, which does change the numbers and is treated as such — and in how much of it the implementation is willing to amortize across iterations and across the callers (regular fitting and forced extraction) that need elliptical sampling. This section explains the four algorithmic choices that together account for the speed gap. Concrete numerical comparisons across image size, sampling density, and configuration combination live in the separate benchmark chapters that draw from the Huang2013, S4G, and SGA2020 campaigns; here we focus on the reasons.

    §1.3.1 Where Python predecessors spend their time

    Three patterns dominate the runtime of the existing Python elliptical-isophote stack. We name them at the abstraction level of "loops vs vectors" rather than by specific function name, since implementations evolve and a citation to a function name in a release notes section would age out within a release cycle.

    Per-point Python-level sampling. The classical formulation samples intensity at \(N\) points around each trial ellipse. A direct implementation evaluates each point through a Python-callable integrator that pulls a small neighborhood of pixels out of the image and returns either the bilinear-interpolated central value or a small area integral. With \(N\) on the order of \(2\pi a\), an isophote at \(a = 100\,\mathrm{px}\) requires more than six hundred such calls per iteration, and there are typically ten to thirty iterations per isophote and tens to hundreds of isophotes per image. Each call is fast in absolute terms but carries Python interpreter overhead, and the cumulative cost is what dominates wall time at the image level.

    Redundant gradient evaluation. The geometry-update step needs the local radial intensity gradient \(dI / da\), estimated by a one-sided difference: the image is sampled at one SMA offset above the current one, and the sample at the current SMA is reused. In the classical algorithm this gradient is re-evaluated on every iteration, even though the geometry typically changes by a few percent per iteration once it has approximately settled. Each gradient evaluation costs one additional sampling pass — an extra ellipse sampled at \(N\) points — so the gradient alone roughly doubles the sampling cost per iteration in the classical formulation.

    Duplicated sampling code paths. Regular fitting and forced photometry extraction both need to sample the image along elliptical paths, but for historical reasons each is implemented with its own sampling helpers. The same operation — "compute the pixel coordinates of \(N\) points along an ellipse with parameters \((x_0, y_0, a, \varepsilon, \mathrm{PA})\) and look up the image intensities at those points" — is written and tested more than once. The duplication is not just a code-maintenance liability; it also means that an optimization applied to one caller does not automatically benefit the other, and that the call sites can drift in their conventions (half-pixel offsets, boundary handling, mask treatment) until they disagree on what "the same isophote" means.

    These three patterns compound. A fit at moderate image size and SMA density is bottlenecked by tens of thousands of Python-level sampling calls, each of which is redundantly invoked through one of several parallel code paths. None of them is individually fatal, but together they set the wall-clock floor.

    §1.3.2 What ISOSTER does differently

    ISOSTER replaces these patterns with four choices. Three are independently speedups — vectorized sampling, the Numba kernels, and the lazy gradient. The fourth, the shared sampling stack, is primarily a maintenance-and-correctness design whose performance effect is indirect: it lets an optimization written once benefit both sampling callers. Together they form the core of the performance argument.

    Vectorized path-based sampling

    The first and most fundamental change is to replace the per-point sampling loop with a single vectorized call into scipy.ndimage.map_coordinates. Given an image array and an array of \(N\) fractional pixel coordinates \((x_j, y_j)\), map_coordinates evaluates a \(k\)-th order spline interpolation at all \(N\) points in a single C-level pass, returning the intensity vector \(\mathbf{I} \in \mathbb{R}^N\) as a NumPy array. ISOSTER uses bilinear interpolation (first-order spline) for the intensity and variance samples and nearest-neighbor for the mask, which matches the accuracy needs of the isophote fit while collapsing the Python loop into one external call. The coordinate array itself is computed analytically from the ellipse parameters in a few NumPy operations. In the default mode the angle \(\theta_j = \phi_j\) is the image position angle, stepped uniformly, and the radius follows the polar equation of the ellipse:

    \[ r_j = \frac{a(1-\varepsilon)} {\sqrt{(1-\varepsilon)^2\cos^2\phi_j + \sin^2\phi_j}}, \]
    \[ x_j = x_0 + r_j \cos\phi_j \cos\mathrm{PA} - r_j \sin\phi_j \sin\mathrm{PA}, $$ $$ y_j = y_0 + r_j \cos\phi_j \sin\mathrm{PA} + r_j \sin\phi_j \cos\mathrm{PA}, \]

    In eccentric-anomaly mode (§1.4.1) the eccentric anomaly \(\psi\) is stepped uniformly instead, with \((x'_j, y'_j) = (a\cos\psi_j,\ a(1-\varepsilon)\sin\psi_j)\) on the principal axes before the same rotation by PA.

    so the entire sampling pipeline — coordinates, interpolation, and mask application — is a small constant number of NumPy / SciPy calls per isophote regardless of \(N\). The Python interpreter is involved only in launching the call, not in iterating over the \(N\) points.

    This single change accounts for the largest share of the speed gap between ISOSTER and the direct Python predecessor. It is also the choice that fixes the loop overhead exactly — there is no "Python loop with \(N\) iterations" left in the sampling layer at all. The remaining Python loops in the fit are over iterations of the per-SMA solver, which numbers in the tens, not over sample points, which number in the hundreds.

    Numba-accelerated inner kernels

    A small number of operations sit between sampling and convergence checking that are awkward to vectorize cleanly in NumPy but are trivially expressible as JIT-compiled loops. The chief examples are the harmonic design-matrix builder \(\mathbf{A} = [\mathbf{1}, \sin\theta, \cos\theta, \sin 2\theta, \cos 2\theta]\) for the five-parameter geometry fit, the ellipse-coordinate construction behind the sampling call above, the harmonic-model evaluation used to reconstruct the fitted model on a ring (for residuals and convergence), and the eccentric-anomaly to position-angle conversion of §1.4.1. ISOSTER implements these with Numba @njit decorators in isoster/numba_kernels.py so that each one compiles to a tight loop in machine code at first call, then runs at speeds comparable to a hand-written C implementation. (The joint multi-band design-matrix builder of §1.4.5 gets the same treatment in isoster/multiband/numba_kernels_mb.py; the dominant-coefficient selection \(\max(|A_1|, |B_1|, |A_2|, |B_2|)\) is a one-line np.argmax in isoster/fitting.py and is not JIT-compiled.)

    Two implementation properties are worth flagging. First, every Numba kernel has a byte-equivalent NumPy fallback in the same file: if the Numba import fails or the user explicitly disables it, the fallback is dispatched transparently and produces identical numerical output. This matters for reproducibility on systems where LLVM is unavailable and for the configuration where ISOSTER is run on a small number of galaxies. The cold-process penalty is real, and §1.6.5 breaks it into the three costs it is usually conflated from: importing the stack (\(0.84\,\mathrm{s}\) (IQR \(0.83\)–\(0.86\)) on the reference machine), reading the compiled kernels back from Numba's on-disk cache on first dispatch (\(0.101\,\mathrm{s}\) (IQR \(0.099\)–\(0.103\))), and genuinely compiling them when that cache is empty (a further \(0.36\,\mathrm{s}\) (IQR \(0.36\)–\(0.37\))). Only the last is compilation, and it is paid once per compatible cache rather than once per installation: a Numba or ISOSTER upgrade invalidates the cached objects, and an environment that cannot write the cache directory pays it every time. This is why an earlier version of this section, which observed the \(0.1\,\mathrm{s}\) cache load on a machine that had already run ISOSTER and called it "JIT compilation", understated the cost by about a factor of four. Second, the kernels are deliberately small. The Numba-compiled region is the design-matrix construction and the coordinate and angle arithmetic; the linear solve itself is delegated to NumPy, which already wraps LAPACK — numpy.linalg.lstsq on the unweighted design matrix in the OLS path, and numpy.linalg.solve on the explicitly formed weighted normal equations in the WLS path of §1.4.2. We do not attempt to JIT-compile the solver, because doing so would require duplicating LAPACK behaviour inside Numba for no measurable gain.

    Lazy gradient evaluation

    The radial gradient \(dI / da\) is the single most expensive quantity in the per-iteration cost budget, because evaluating it requires one additional sampling pass at an SMA offset from the current isophote. The classical formulation re-evaluates it every iteration. ISOSTER instead computes the gradient on iteration \(i = 0\), caches the value, and reuses it on every subsequent iteration of the same isophote unless one of three conditions forces a re-evaluation: the dominant harmonic amplitude \(|a_\max|\) fails to improve for three consecutive iterations; the cached value carries no usable uncertainty; or a gradient-quality strike is currently outstanding (§1.4.6). The last condition matters more than its size suggests — a cached gradient computed before the first strike is exactly the value whose reliability the strike is questioning, so reusing it would let a stale number decide whether to record a gradient failure.

    The justification for caching at all is that the gradient is a local property of the image at the current geometry. Once the iteration is reasonably close to the converged isophote, the geometry moves by a few percent per iteration and the gradient changes by less, because the gradient is itself a slowly varying function of \(a\) wherever the fit is well conditioned. The stall detector is an inexpensive safeguard for the case where the cached value is meaningfully wrong — for instance when the iteration has wandered into a region of low gradient SNR — and restores the classical behaviour there at the cost of a few extra sampling passes on the affected isophote.

    What it saves. On a representative fit — an \(n = 2\) Sérsic model, \(R_e = 30\,\mathrm{px}\), \(\varepsilon = 0.4\), \(S/N = 50\), 59 isophotes from \(a_0 = 10\) to \(a_\max = 120\,\mathrm{px}\) — the lazy path performs 60 gradient evaluations against 414 for the classical path — a factor of \(6.9\), and the one figure here that is exactly reproducible, since it is a count rather than a time. The wall-clock saving that follows has a median of \(24\%\) across eighteen sessions, with an interquartile range of \(23.0\%\) to \(24.1\%\).

    We quote the median and the interquartile range, and deliberately not the extremes, because the extremes are not a stable statistic here. In the archived set the individual sessions fall between \(22.2\%\) and \(24.4\%\). That looks tight, and within a single archive it is; but an earlier eighteen-session archive on the same machine contained a session that returned a negative saving, with the cached path running slower. We did not diagnose it. The result is consistent with external load on the machine during that session, which is the usual cause, but we did not instrument the run and cannot say so; it stands as an unexplained timing outlier. That is the point: the width of the extremes is itself a property of the particular run, and quoting it would present as a measured bound something that changed by a factor of several between two archives taken on one machine. The median and the quartiles reproduce across independent sets to within a percentage point; the minimum and maximum do not reproduce at all. Earlier drafts of this section quoted min-to-max intervals from three sessions and had to revise them three times, which is what that instability looks like from the inside. The evaluation count remains the robust part of the result — what it converts into depends on how much of a given fit is sampling, which varies with the galaxy and the configuration (reproduced by benchmarks/draft_timings/run_draft_timings.py --sessions 18; measurement protocol in §1.6.5). Note that the iteration count is essentially unchanged (414 against 414 here). The saving is in sampling passes per iteration, not in shorter iteration sequences, and describing it as "fewer iterations" would misattribute where the time goes.

    What it costs. This is the only change in §1.3.2 that is not a pure software-engineering optimization: it modifies the algorithm. Because a cached gradient differs slightly from the freshly evaluated one, each geometry update differs slightly, and the differences accumulate along the iteration trajectory. The converged output is therefore not identical to the classical path, and it is worth being precise about the size of the difference rather than asserting equivalence. Comparing use_lazy_gradient=True against False on the fit above, and on the same model at two other noise levels:

    \(S/N\) median \(\lvert\Delta\rvert / \sigma\) max \(\lvert\Delta\rvert / \sigma\) max \(\lvert\Delta x_0\rvert\) (px) max \(\lvert\Delta\mathrm{PA}\rvert\) (rad)
    200 \(3 \times 10^{-4}\) 0.22 0.0036 0.0031
    50 \(1 \times 10^{-3}\) 1.6 0.64 0.013
    10 \(4 \times 10^{-3}\) 2.6 3.0 0.072

    (\(\Delta\) is the difference in a geometry parameter between the two modes; \(\sigma\) is that parameter's own reported uncertainty on the same isophote. The first two columns aggregate over \(x_0\), \(y_0\), \(\varepsilon\) and PA. Every entry is a median across eighteen noise realisations of the same model — one per session, since the difference between two converged fits is fixed once the image is fixed, so a single realisation would report a spread of zero rather than no spread at all. Run-to-run variation in the tail is appreciable: across those realisations the \(S/N = 50\) maximum has an interquartile range of \(1.2\)–\(1.9\) and individual realisations range from \(0.81\) to \(2.6\). The column to read is therefore the order of magnitude, not the digits.)

    The pattern is the honest summary of the trade. For the overwhelming majority of isophotes the two modes agree to a small fraction of the fitted uncertainty — the median disagreement stays below one percent of \(\sigma\) at every noise level tested. But the tail grows sharply as the data get noisier: at \(S/N = 200\) the worst isophote in the sequence moves by about a fifth of its own uncertainty, while at \(S/N = 10\) it moves by more than \(2\sigma\) and its centre by a few pixels. This is the expected behaviour rather than a defect: the low-gradient, low-SNR regime is exactly where a cached gradient is least representative and where the geometry update is most sensitive to it. It does mean that the lazy gradient should be understood as a fast approximation rather than an exact reformulation, and that a user pursuing per-isophote geometry in the LSB outskirts — the regime of §1.4.3 — has a defensible reason to set use_lazy_gradient=False and pay the roughly 31% surcharge.

    Shared sampling stack

    The fourth change addresses the duplicated-sampling-path pattern of the classical Python implementations. ISOSTER has one sampling module (isoster/sampling.py) that exposes one entry point (extract_isophote_data) and one return type (IsophoteData). Both sampling callers route through it:

    • Regular fitting (isoster/fitting.py) calls it on each iteration of each isophote.
    • Forced photometry extraction (extract_forced_photometry in the same module) calls it once per template isophote with the template geometry held fixed.

    2-D model reconstruction (isoster/model.py) is the exception, and naming it matters because the earlier version of this section claimed it as a third caller. It does not sample along elliptical paths at all: it solves the opposite problem. Sampling asks "what is the image intensity at these \(N\) points on this ellipse"; model reconstruction asks "what intensity does the fitted model assign to every pixel in this grid", which it answers by determining each pixel's semi-major-axis coordinate under the locally interpolated geometry and evaluating a radial interpolant of the fitted intensities there. That is a different operation with a different kernel (scipy.interpolate.interp1d over the isophote list, not map_coordinates over the image), so it neither shares the sampling stack's mask and boundary conventions nor inherits its optimizations.

    A bug fix to mask treatment, a change to the boundary-handling convention, or an optimization to the coordinate-construction arithmetic therefore lands once and benefits both sampling callers. The half-pixel offset convention is enforced in one place for them. The sampling output schema — what IsophoteData carries — is the same wherever sampling happens.

    This is a software-engineering argument, not directly an algorithmic-speed argument. Its one concrete performance consequence is that optimizations to the shared sampling stack amortize across both sampling callers; in particular, the vectorized-map_coordinates choice automatically benefits forced photometry in addition to regular fitting, which is significant because forced photometry is the dominant workflow in multi-band survey pipelines. Separately, the multi-band extension (§1.4.5) was buildable as a parallel module precisely because the single-band sampling stack was self-contained: the multi-band path imports the low-level coordinate helpers without having to also inherit the sampling callers' historical peculiarities.

    §1.3.3 Algorithmic complexity and where it goes

    The four choices in §1.3.2 do not change the asymptotic complexity of the algorithm — they reduce the constant factors. It is worth naming the asymptotic structure explicitly so that the speed argument can be quantified later without ambiguity.

    Per-isophote cost is dominated by two terms. The sampling step performs \(N = \max(64, \lfloor 2\pi a \rfloor)\) interpolations through one map_coordinates call, costing \(\mathrm{O}(N)\) in image-area terms and \(\mathrm{O}(1)\) in the Python interpreter. The linear-system solve is \(\mathrm{O}(p^2 N)\) where \(p\) is the number of fit parameters (five for the geometry-only fit, \(5 + 2L\) for an extended ISOFIT fit with \(L\) higher orders, and \(B + 4 + 2L\) for a multi-band joint fit with \(B\) bands; see §1.4.1 and §1.4.5). Both terms are linear in \(N\), so per-isophote cost is asymptotically linear in the semi-major axis \(a\) and effectively independent of image area beyond what enters through map_coordinates' interpolation kernel.

    Image-level cost is the per-isophote cost summed over the inward and outward growth loops. Let \(K\) be the number of isophotes (typically of order 50 in a geometric-stepping fit from \(a_0 = 10\,\mathrm{px}\) to \(a_\max = 200\,\mathrm{px}\) with astep = 0.1), and let \(\overline{m}\) be the average per-isophote iteration count. Worst-case total cost is \(\mathrm{O}(K \cdot \overline{m} \cdot N_\max)\) where \(N_\max\) is the sample count at the largest SMA. In practice \(\overline{m}\) is well below the configured maxit because most isophotes converge in under twenty iterations, and the lazy-gradient optimization makes \(\overline{m}\) matter less because each additional iteration costs just one sampling pass rather than two.

    The two consequences worth pointing out:

    • Image area enters only through map_coordinates interpolation cost. The interpolation kernel reads a small neighborhood (\(k+1\) pixels per dimension for a \(k\)-th order spline) around each of the \(N\) sample points. The total pixel reads per isophote is therefore \(\mathrm{O}(N \cdot k^2)\) — sublinear in the image area for any modern image size. This is why the fit time scales with the number of isophotes and the typical semi-major axis, not with the image dimensions, in the regime where the galaxy occupies a small-to-moderate fraction of the image.

    • Sampling density and ISOFIT cost. The user-facing knobs that most strongly affect runtime are astep (geometric SMA step, which sets \(K\)) and the harmonic-fit configuration (which sets \(p\), and therefore the LAPACK solve cost). The ISOFIT path with harmonic_orders=[3, 4] carries \(p = 9\) rather than \(p = 5\), raising the solve cost by a constant factor that the benchmark chapters quantify in absolute terms.

    The point of this complexity sketch is not to predict wall time but to clarify which knobs in IsosterConfig are the runtime-relevant ones. The benchmark chapters then quantify the constants.

    §1.3.4 Correctness guarantees alongside speed

    The performance argument is only useful if the faster code computes the same thing as the slower code where the algorithm overlaps. ISOSTER provides three guarantees that together establish this:

    1. Plain OLS path when variance_map = None. The weighted-least-squares (WLS) machinery introduced in §1.4.2 is only engaged when the user supplies a variance map; in its absence, the linear-system solve is the ordinary unweighted least-squares solve used by every classical implementation (NumPy's SVD-based least-squares driver on the design matrix itself, rather than the explicitly formed normal equations the weighted path uses), so given identical sampled data the fitted coefficients agree to within the floating-point determinism of LAPACK on the host platform. The configuration flag is therefore binary at the algorithm-correctness level: variance_map is either supplied (WLS) or it is not (OLS), and the two paths share no shared mutable state.

    2. Round-trip serialization preserves the fit and its configuration. Saving a fit through isophote_results_to_fits and reading it back through isophote_results_from_fits recovers the per-isophote values and reconstructs an IsosterConfig whose fields match the original; the same holds for the ASDF writer–reader pair, and the META HDU carries the top-level result keys that are neither per-isophote nor configuration fields so that they survive too. Because the CONFIG HDU records the resolved configuration — every field, including those the user left at their default — the settings need never be supplied out of band, and a default that changes between releases cannot silently alter the meaning of an existing file. What we claim is reproducibility of the configuration, not of the fit from the file alone: the file contains neither the image, the mask nor the variance map, and reproducing the numbers additionally depends on the ISOSTER version, the host LAPACK, and whether the Numba kernels were available.

    3. Regression-test coverage of the fast paths. The test suite pins the Numba kernels against their NumPy fallbacks element-by-element — design-matrix construction, ellipse coordinates, harmonic-model evaluation, and the eccentric-anomaly conversion — including the degenerate and high-ellipticity cases where the two implementations would be most likely to diverge. Serialization round-trips, the stop-code contract, and the per-feature behaviour of each configuration flag are covered at the per-SMA dictionary level on synthetic galaxies generated deterministically from seeded factories rather than from stored reference files. The suite runs on every commit.

    Two things §1.3.4 deliberately does not claim. It does not claim a specific numerical-agreement number with photutils.isophote, Isofit, or AutoProf; those are quantitative empirical questions that the benchmark chapters answer on representative samples. And it does not claim that every fast path is output-identical to its slow counterpart. Three of the four choices in §1.3.2 are: vectorized sampling, the Numba kernels, and the shared sampling stack all compute the same numbers as the implementations they replace. The lazy gradient does not, by construction, and §1.3.2 quantifies the difference rather than asserting it away.
